# Cloudflare 게시

## 사용 순서

1. Cloudflare 연결 화면에서 R2·Pages 설정과 공개 주소 이름을 저장한다.
2. 프로필을 편집하고 영상 인코딩을 완료한다.
3. **공개본 만들기 → 새 공개본 만들기 → 미리보기**로 공개 정보를 확인한다.
4. 해당 공개본의 **게시**를 누르고 공개 주소·대상 Pages 프로젝트·미디어 용량을 확인한다.
5. `게시되었습니다` 안내 후 표시된 주소를 브라우저에서 연다. 예: `https://onfilm.co.kr/actor_01/`.

이 작업은 연결된 **Pages 프로젝트 전체**를 선택한 공개본으로 교체한다. 같은 프로젝트에 다른 사이트를 함께 보관하는 용도가 아니다. 로컬 편집 내용은 자동 게시되지 않는다. 수정 후 새 공개본을 만들어 게시해야 한다. ZIP을 수동 업로드할 필요는 없다.

## 무엇을 올리는가

- R2: 공개본에 포함된 대표 사진·갤러리·섬네일·인코딩된 원본/트레일러 HLS. 편집용 원본 영상은 제외한다.
- Pages: HTML·JS·CSS·아이콘·공개 프로필 JSON. `/<주소이름>/` 아래에 배치한다.
- 공개 진입 주소 `/<주소이름>/`는 유지하고, HTML의 기준 주소를 `/<주소이름>/releases/<배포 지문>/`으로 고정한다. JSON·JS·CSS·사진·영상이 같은 배포 경로를 사용하며 버전별 `media/*` 요청만 해당 R2 묶음으로 302 연결한다. HLS 재생/트레일러도 이 기준 주소로 해석한다.
- 진입 HTML은 `no-store`, 버전별 파일은 장기 캐시한다. 파일명이 같은 사진을 교체하거나 프로필 정보만 수정해도 새 배포 주소를 사용한다. 구버전 미디어 주소를 신버전 파일로 연결하지 않는다. 로컬 공개본/ZIP의 상대경로는 그대로 유지한다.
- 이 수정은 업데이트된 앱으로 새 공개본을 생성하고 게시해야 반영된다. 이전 구현의 캐시가 남은 방문자는 공유용 기본 주소를 다시 열고 새로고침해야 할 수 있다. 이미 열린 과거 페이지의 무중단 재생은 보장하지 않으며, 기존 R2 정리 정책에 따라 과거 파일이 삭제되면 최신 기본 주소로 다시 접속해야 한다.
- `/`는 현재 공개 주소로 이동한다. 존재하지 않는 페이지는 404로 처리한다.
- API 키·로컬 DB·작업 기록·백업은 업로드하지 않는다. 원래 로컬 공개본과 ZIP도 변경하지 않는다.

## 진행·실패·재시도

- R2 업로드 진행률은 **완료한 파일의 바이트 합계** 기준이다. 큰 파일 하나를 전송하는 동안 퍼센트가 잠시 멈출 수 있다.
- 게시 중 앱 종료·백업/복원·공개본 휴지통 이동·연결 설정 변경을 막는다. `업로드·결과 대기 중단`으로 로컬 작업을 중단할 수 있다. 이미 접수된 Pages 배포는 계속 완료될 수 있다.
- 새 게시마다 `onfilm/v2/<project>/<UUID>/media/` 전용 경로를 사용한다. 동일 공개본도 새 게시라면 다시 업로드한다. 삭제 대상 경로를 다른 게시 작업이 재사용하지 않도록 하는 안전 장치이며, PUT 요청량과 게시 중 임시 저장 용량이 늘어나는 비용이 있다. 같은 업로드 작업 내에서는 HEAD로 크기·해시 메타데이터를 확인한다.
- 모든 R2 파일과 Pages 화면 업로드 후에만 운영 배포를 요청한다. Pages API의 production/deploy/success 응답을 확인해야 성공으로 표시한다.
- 마지막 성공 기록은 실패 시 지우지 않는다. 네트워크 장애로 상태를 확인하지 못한 경우 실패라고 단정하지 않고 **이전 배포 결과 확인**을 제공한다.
- Pages 접수 전에 고유한 요청 표식을 로컬에 기록한다. 배포 응답이 유실돼도 앱 재시작 후 표식으로 서버 기록을 찾아 결과를 확인하며 같은 요청을 무조건 재발행하지 않는다.
- 서버에서 배포 실패·거부가 확인되면 다시 게시할 수 있다. 접수 여부가 불명확하고 표식도 조회되지 않으면 새 배포를 차단한다. 이 드문 경우에는 Cloudflare 대시보드에서 진행 중인 배포 여부와 앱의 요청 표식을 확인해야 한다. 자동 강제 재배포·기록 초기화는 제공하지 않는다.
- 오류 메시지에는 원격 응답 본문이나 키를 노출하지 않는다.

## 비용과 남은 범위

R2 HEAD·PUT·LIST·DELETE 및 저장 공간 사용이 발생한다. 무료 한도나 요금이 자동 보장되는 기능은 아니다. 새 게시 성공 및 로컬 영수증 저장 후, 같은 버킷·프로젝트에서 이 앱이 기록한 이전 전용 묶음과 실패한 업로드 묶음을 정리한다. 각 삭제 배치 전 Pages canonical production 배포가 방금 성공한 배포와 같은지 재확인한다. 실패·불확실한 게시에서는 삭제하지 않는다. 정리 실패는 게시 성공을 취소하지 않으며 영수증의 대상을 다음 게시 성공 시 재시도한다.

`onfilm/v1/` 구버전 파일, 다른 PC가 게시한 경로, 기록을 잃어버린 파일, 다른 버킷은 추측으로 삭제하지 않는다. 로컬 편집만으로는 R2를 정리하지 않는다. 삭제는 복구되지 않으며 과거 배포 롤백·열어둔 과거 페이지/캐시의 미디어는 더 이상 보장되지 않는다. 최신 페이지로 새로고침하거나 과거 공개본을 새로 게시해야 한다. Cloudflare 대시보드의 수동 롤백과 삭제는 원자적으로 묶을 수 없으므로 앱 게시·정리 중 외부에서 배포를 바꾸지 않는다. 여러 PC의 게시 조율은 미지원이다.

구버전·다른 PC 파일 정리, 원격 사용량 표시는 별도 후속 작업이다. 게시 완료는 Pages API 기준이며, 커스텀 도메인의 DNS·R2 CORS까지 확인했다는 뜻은 아니다. 실제 공개 주소에서 사진·트레일러·영상 탐색을 확인해야 한다. R2 CORS에 공개 사이트 출처를 허용해야 한다. `pages.dev` 주소로 확인하려면 해당 출처도 별도 허용해야 한다.

## 게시 종료

1. Cloudflare 연결에서 R2 관리 API Token을 저장한다(계정 Workers R2 Storage Edit). 기존 Pages 토큰에도 배포 삭제 권한이 필요하다.
2. 공개본 화면에서 `게시 종료`를 누르고 프로젝트·버킷·주소 및 삭제 범위를 확인한다.
3. 포트폴리오 대신 종료 안내 `404.html`을 운영 배포한다. `/`, 프로필 주소, 개별 페이지 모두 콘텐츠 없는 종료 화면으로 응답한다.
4. 선택한 버킷의 모든 Custom Domain 및 r2.dev 공개 접근을 비활성화하고 다시 조회한다.
5. 확인 시점에 존재했던 과거 Pages 배포를 삭제한다. 현재 종료 배포는 남긴다. 과거 배포 URL 삭제는 복구되지 않는다.

한 사람 전용 Pages 프로젝트/R2 버킷을 전제로 한다. 같은 프로젝트의 다른 사이트와 같은 버킷의 다른 파일도 공개가 중단되므로 공유 리소스에는 사용하지 않는다. R2 객체·로컬 원본·DB·백업은 삭제하지 않으며 저장 비용은 계속 발생할 수 있다.

종료 과정은 로컬 영수증에 준비/접수/대기/정리/완료 상태로 기록한다. 응답 유실 시 요청 표식으로 배포를 찾고 무조건 새 배포하지 않는다. 일부 실패는 완료로 표시하지 않으며 `게시 종료 재시도`로 이어간다. 미완료 종료가 있으면 새 게시를 막는다. 종료된 뒤 공개본을 게시하면 성공 배포 확인 후 설정한 미디어 도메인 하나만 다시 활성화한다.

안전 제한: 과거 배포 최대 200개, 진행 중인 외부 배포가 없어야 한다. 종료 도중 외부 배포/도메인 추가 또는 canonical 배포 변경을 발견하면 중단한다. Cloudflare 설정과 배포를 수동으로 동시에 변경하지 않는다. 여러 PC 및 외부 변경과 원자적으로 조율하지는 않는다.

종료는 API에서 확인한 공개 설정 기준이다. 이미 다운로드한 파일·브라우저 캐시는 회수하지 않으며, 별도 Worker/R2 바인딩·서명 URL·다른 사이트의 복사본까지 차단하지 않는다. CDN 캐시 삭제도 이 기능에는 포함되지 않는다. 실제 공유 주소·과거 배포 주소·직접 미디어 주소는 별도 브라우저에서 확인한다.

## 구현·검증

Electron main의 제한된 export-page IPC만 게시를 수행한다. renderer는 키나 임의 파일 경로를 전달할 수 없다. 암호화 연결 설정과 비밀값 없는 배포 영수증은 사용자 데이터 옆 `.connections` 폴더에 보관되어 프로필 백업에 포함되지 않는다. 복원된 프로필과 마지막 게시본은 서로 다를 수 있다.

Cloudflare의 [Direct Upload 배포 API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/subresources/deployments/methods/create/), [공식 Wrangler 업로드 구현](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/pages/upload.ts), [파일 해시 규칙](https://github.com/cloudflare/workers-sdk/blob/wrangler%404.45.0/packages/wrangler/src/pages/hash.ts)을 기준으로 업로드 JWT, BLAKE3 콘텐츠 해시, manifest와 `_redirects`/`_headers` multipart를 구성한다. 외부 CLI나 추가 Node 설치 없이 앱의 런타임 의존성을 사용한다.

테스트는 가짜 자격증명·모의 Cloudflare 응답·임시 파일 H2 및 분리된 로컬 HTTP 미디어 서버만 사용한다. 실제 계정의 게시 결과와 Windows 설치 앱 동작은 별도로 검증해야 한다.
